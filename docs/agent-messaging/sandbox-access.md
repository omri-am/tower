# Codex permission entries that let a sandboxed agent run tower

Measured on macOS from 2026-10-15 to 2026-10-18, with the real `~/.codex/packages/standalone/releases/0.162.1-aarch64-apple-darwin/bin/codex` (`codex-cli 0.162.1`) and the model `gpt-6-luna`. Each run logged `"version": "codex-cli 0.162.1"` at start and `installed_after` as `0.162.1-aarch64-apple-darwin` at the end. These are results for **codex-cli 0.162.1**, not a general claim about Codex.

The [probes](sandbox-probes/) reuse T038's harness from [`lifetime-probes/common.py`](lifetime-probes/common.py) without edits. So each run used a fresh `~/.cache/tower-t038-probes/tmp.*` fixture with a repository `repo/`, a linked worktree `wt/` with a `.tower` symlink, and the state root `repo/.git/tower/root`. Every run started from the owner's `workspace` profile (`":minimal" = "read"`, project roots writable, in the `[permissions.workspace.filesystem]` sections of `~/.codex/config.toml`). The candidate entries were added with one run-only override, because a dotted `-c` key splits a path at its dots: `-c 'permissions.workspace.filesystem={":minimal"="read", ":project_roots"={"."="write"}, "<path>"="read", ...}'`. Before it builds the override, the probe checks that `config.toml` still holds those two base entries. No run passed `--sandbox`.

[`p1_sandbox_matrix.py`](sandbox-probes/p1_sandbox_matrix.py) runs five commands through `codex sandbox -P workspace --log-denials` in the worktree: `tower --help`, `tower-register --help`, `python3 -c ...`, `bash -c 'git rev-parse --show-toplevel'`, and a `runtime_root` command that imports `tower_msg` and calls `runtime_root()`. That function runs `tower-locate` and `git rev-parse`, which are the external commands that `register()` runs before it writes. [`p2_live_session.py`](sandbox-probes/p2_live_session.py) runs an interactive TUI under `env -i` with the entries and `--add-dir <git common dir>/tower`.

In this document, **pass** means that the probe observed the behaviour that the question asks about. **fail** means that the probe observed its absence. **cannot determine** means that the probe did not reach the observation. A p1 case passes when all five commands exit 0 and the sandboxed output of `tower --help`, `runtime_root` and `bash_git` equals the unsandboxed output.

## Question 1: a general rule, then the owner's entries

Codex resolves a profile path to its target, so an entry for a symlink does not open the link itself (**inferred** from [`tmp.ouqVwros`](sandbox-probes/logs/tmp.ouqVwros/p1_sandbox_matrix.jsonl), where the entry `/opt/homebrew/opt/pyenv` still left `file-read-metadata /opt/homebrew/opt/pyenv` denied). A user on any machine derives the entries with this rule:

1. Run `command -v` for `tower`, `tower-register`, `python3` and `git` with the `PATH` that the agent gets. For each result, follow every symlink, and every script it runs, to a real program.
2. Add the directory that holds each symlink on that path, and the install directory of each real program.
3. Add the install directory of each library that the real program loads at start, and the directory that holds each link in that library's load path. `otool -L` lists the candidates. Only some were needed here.
4. Add `sys.base_prefix` of that `python3`.
5. Add each git config file that `git config --list --show-origin` names when it runs in the project's worktree. Git exits with a fatal error when it cannot read one.
6. Add the project's git common dir, from `git rev-parse --path-format=absolute --git-common-dir` in the worktree.

The `git` row hides its failure from tower. Bash, which runs `bin/tower-locate`, skips `/opt/homebrew/bin/git` when its target is unreadable and runs the Xcode stub `/usr/bin/git` instead. `tower-locate:43` sends that error to `/dev/null`. In the fixture, the `.tower` symlink lets `tower-locate` succeed without git, so `runtime_root` still printed the right state root. Other layouts are **inferred** to go wrong from reading `bin/tower-locate`, not measured. When git fails, `CUR_TOP` stays empty, so `is_per_branch_copy` returns false (`bin/tower-locate:56`) and the main-checkout mapping is skipped (`bin/tower-locate:72`). A per-branch `.tower` copy in a linked worktree then resolves as `ancestor`, which is the wrong project. This is why `bash_git` is part of the verdict.

Some candidates were not needed. The deciding `all` case in `tmp.UY474pYr` passed without `openssl@3`, `readline` and `xz`, although `otool -L` lists them for `python3.10`. It also passed without `~/.config/git` and without `~/.claude/plugins/installed_plugins.json`. Earlier runs with weaker verdict rules showed the same: [`tmp.SJNPb0H1`](sandbox-probes/logs/tmp.SJNPb0H1/p1_sandbox_matrix.jsonl) for the libraries, [`tmp.L9v1bWzQ`](sandbox-probes/logs/tmp.L9v1bWzQ/p1_sandbox_matrix.jsonl) for `~/.config/git` and [`tmp.3GWaynJl`](sandbox-probes/logs/tmp.3GWaynJl/p1_sandbox_matrix.jsonl) for the registry file. The owner has no `~/.config/git/config`, only an `ignore` file, and git only warns when it cannot read that file: `call2.err` in `tmp.QJ5yUSxr` holds `warning: unable to access '/Users/omriam/.config/git/ignore': Operation not permitted`. Without the registry file, `tower` is **inferred** from its `from_cache` function to fall back to the newest cached version, which is the same `0.6.0` here. With two cached versions the fallback could differ, which was not measured.

### What this setup did not cover

The p1 matrix did not follow the `~/.local/bin` links that bootstrap makes. On this machine `~/.local/bin` holds `tower-*` links to `~/.local/libexec/tower-shim`, but no `tower` or `tower-register` link, because plugin `0.6.0` has neither command. The agent's `PATH` lists `~/Documents/personal-projects/tower/bin` first, so both commands resolved to the checkout. A hand check, saved as [`logs/hand-checks/bootstrap-chain.txt`](sandbox-probes/logs/hand-checks/bootstrap-chain.txt), ran `~/.local/bin/tower-locate` by its full path with `~/.local/bin` first on `PATH`. Under the 12 entries plus `~/.gitconfig-personal` it failed: `/bin/bash: /Users/omriam/.local/bin/tower-locate: Operation not permitted` and `exit=126`. With `~/.local/bin` and `~/.local/libexec` added it printed the worktree, `ancestor` and `exit=0`. In the same check without those two entries, `command -v tower-locate` named the checkout's copy, not the bootstrap link. So bash silently skipped the unreadable `PATH` entry. A bootstrap-only user therefore needs both directories, by rule steps 1 and 2. That check named both directories together, so it does not show that each one alone is needed. Whether `tower` and `tower-register` work through bootstrap links is **cannot determine** here.

Two entries depend on the project, not on the machine. All worktrees of one repository share one git common dir, so the profile needs one common-dir entry for each repository that tower dispatches into. The fixture needed a new entry for each run only because each fixture is a new repository. For the owner's tower repository the common dir is `~/Documents/personal-projects/tower/.git`, which the install-root entry already covers. The owner's `~/.gitconfig:10` also includes `~/.gitconfig-personal` for git dirs under `~/Documents/personal-projects/`. The fixture is outside that directory, so p1 did not meet the include. A hand check in this T045 worktree, saved as [`logs/hand-checks/gitconfig-include.txt`](sandbox-probes/logs/hand-checks/gitconfig-include.txt), ran `git rev-parse` under 11 entries: the 12 without the fixture's common dir. Without `~/.gitconfig-personal` it printed `fatal: unable to access '/Users/omriam/.gitconfig-personal': Operation not permitted` and `exit=128`. With that entry it exited 0. So for the owner's real tower worktrees the profile also needs that file. How the later dispatch card covers these two entries is that card's decision.

## The launcher's PATH decides what the agent can find

The tool call's `PATH` is the launcher's `PATH` with Codex's own directories in front. With a system `PATH` launcher, [`tmp.TN38cRgr`](sandbox-probes/logs/tmp.TN38cRgr/p2_live_session.jsonl) logged a tool-call `PATH` of Codex's directories plus `/usr/bin:/bin:/usr/sbin:/sbin`, then `zsh:1: command not found: tower`. With the owner's terminal `PATH` and no entries, [`tmp.xEJAMdPW`](sandbox-probes/logs/tmp.xEJAMdPW/p2_live_session.jsonl) found tower but could not run it: `zsh:1: operation not permitted: tower`.

Dispatch in its default mode opens a new Terminal window (`bin/tower-dispatch:172-176`). In `here` and `headless` modes it starts Codex with the dispatcher's environment (`lib/tower-dispatch.sh:201`). In both cases the agent gets a terminal's `PATH`, so the live runs used `env -i` with the `PATH` of a new terminal login shell, not T038's system `PATH`. A dispatcher whose `PATH` lacks tower gives an agent that cannot find tower, whatever the entries.

Codex runs each tool call as `/bin/zsh -lc`. The rollout of the `tmp.uyfJeFw3` session shows `"command":["/bin/zsh","-lc",...]`, and that rollout is not in the logs. `/etc/zprofile` runs `path_helper`, which moves the system directories to the front. In a hand-run `codex sandbox ... /bin/zsh -lc 'command -v python3'`, `python3` resolved to `/usr/bin/python3`, the Xcode stub, which fails inside the sandbox. That hand run is not in the logs. In the live sessions the tool call found the pyenv shim first. A shell snapshot that Codex wrote at session start held `export -T PATH path=( /Users/omriam/Documents/personal-projects/tower/bin ...`. That the snapshot restores the order after `path_helper` is **inferred**.

## Questions 2 to 4: the holder survives the session

The live run `tmp.QJ5yUSxr` used the 12 entries and `--add-dir .../repo/.git/tower`. The session logged `CODEX_PERMISSION_PROFILE=workspace` and `CODEX_SANDBOX=seatbelt`, so the profile was in effect. The second turn started `tower-register` through the `python3` on `PATH` with `os.setsid()`, as T038 did, and waited for the session line. `/usr/bin/python3` cannot be used for that step inside the sandbox, because there it is the Xcode stub.

The holder registered and held its lock after its own turn (question 2). It held the lock after `ls -la`, `git status --short` and `tower --help`, each in its own turn (question 3). Its `ps` row, with PPID 1 and its own process group, did not change between those checks.

The TUI exited normally 1.2 seconds after the Enter key that followed `/quit`, with status 0. Five seconds later the holder still ran and held its lock (question 4). So "the holder is alive" does not mean "the agent is alive" after a normal exit either. Because the holder left the TUI's process group and session when it started, the TUI's exit is **inferred** not to reach it. How M5 stops the holder at session end is M5's decision. The probe's cleanup then stopped it: `cleanup` `"signalled": true, "exited": true, "lock_free": true`.

## The doctor check

A `tower doctor` check can run these three commands from the worktree, with the user's `PATH`, and require exit 0 from each:

```sh
codex sandbox -P <profile> -C <worktree> -- tower-register --help
codex sandbox -P <profile> -C <worktree> -- /bin/bash -c 'git rev-parse --show-toplevel'
codex sandbox -P <profile> -C <worktree> -- python3 -c 'import sys; sys.path.insert(0, sys.argv[1]); import tower_msg; print(tower_msg.runtime_root())' <tower install root>/lib
```

The measured runs added `-c check_for_update_on_startup=false`, the profile override and `--log-denials` to the same command line, because the probe could not change `config.toml`. A doctor that reads the user's own profile needs no override. The output below is from [`tmp.UY474pYr`](sandbox-probes/logs/tmp.UY474pYr/p1_sandbox_matrix.jsonl).

| Case | `tower-register --help` | `bash -c 'git rev-parse ...'` | `runtime_root` |
| --- | --- | --- | --- |
| pass (`all`) | exit 0, `usage: tower-register [-h] --vendor VENDOR [--vendor-version VENDOR_VERSION]` | exit 0, `.../tmp.UY474pYr/wt` | exit 0, `.../tmp.UY474pYr/repo/.git/tower/root` |
| fail (`none`) | exit 126, `bash: /Users/omriam/Documents/personal-projects/tower/bin/tower-register: Operation not permitted` | exit 1, `xcode-select: error: No developer tools were found ...` | exit 126, `bash: /Users/omriam/.pyenv/shims/python3: Operation not permitted` |
| fail (`minus-keg_git`) | exit 0, the same usage line | exit 1, the same Xcode stub error | exit 0, the same state root |
| fail (`minus-git_global_config`) | exit 0, the same usage line | exit 128, `fatal: unable to access '/Users/omriam/.gitconfig': Operation not permitted` | exit 1, `Command '['git', '-C', '.../wt', 'rev-parse', '--show-toplevel']' returned non-zero exit status 128.` |

Each command catches a failure that another one misses. `tower-register --help` imports `tower_msg` but runs no git. `runtime_root` misses the bash lookup of `git`. The check does not cover the plugin-cache case, where `tower --help` exits 0 but resolves a different root. A check for that compares the sandboxed `tower --help` output with the unsandboxed output, as p1 does. The check also does not cover the write to the state root, which `--add-dir` grants. It passes only in a repository whose git common dir the profile covers: without that entry, `bash_git` and `runtime_root` both fail with `fatal: not a git repository: (null)`. A doctor should use the exit status alone. `--log-denials` is not reliable: in `tmp.UY474pYr`, every command of the `none` case printed `None found.` although each one was denied, with the Claude sandbox off.

## Sources

Every run's JSONL log is kept in [`sandbox-probes/logs/`](sandbox-probes/logs/), one directory per run, named after its `~/.cache/tower-t038-probes/tmp.*` directory. `logs/hand-checks/` holds the one hand check that was saved. The excerpts list selected fields of one event each, and the logs store keys in sorted order, so an excerpt is not always a literal substring. [`sandbox-probes/README.md`](sandbox-probes/README.md) gives the launch lines and each probe's verdict rule.
