# M5a Codex thread identity

Measured on macOS, 2026-10-01, with the real `~/.codex/packages/standalone/releases/0.159.3-aarch64-apple-darwin/bin/codex` (`codex-cli 0.159.3`) and the cheapest available model, `gpt-6-luna`. Live probes launched interactive `codex` TUIs in `mktemp -d` directories under `env -i` with only HOME, USER, LOGNAME, SHELL, TERM, LANG, TMPDIR, CODEX_HOME, a system PATH, and CODEX_BIN. The p1 run in `tmp.xg4MsFPk5X` reused p2's directory to read `session-env.json`. The measured 0.159.3 runs accepted only workspace trust, approved no tool or permission dialog, used the default sandbox and `-c approvals_reviewer="user"`, and passed no bypass flag. Launches also set `check_for_update_on_startup=false` and a scratch `notify` recorder. The harness changed between runs for trust detection, dialog handling, p1 logging, and p4 environment capture. The p4 twins and p2 `inherit="none"` runs used that revision. After the runs, review fixes changed only dialog handling, process cleanup, logging, and the stdin of non-PTY commands, which is now closed. No run used the final revision, and those fixes did not change what the probes measure. Earlier p4 did not capture environment files, so option 4 cites the twins. These are results for **codex-cli 0.159.3**, not a general claim about Codex. After this measurement, the installed Codex moved to `codex-cli 0.162.1`, and re-verification on the installed version is T038's job.

`codex agents --help` says `Usage: codex agents [OPTIONS]` and describes browsing the shared local app-server daemon. The [p1 help sweep](identity-probes/p1_self_command.py) logged 72 commands on codex-cli 0.159.3 and found no command or flag that prints the calling session's id. The 0.159.2 sweep found none either. With `session-env.json` captured from an earlier p2 TUI (`TERM=dumb`, not p1's own thread), p1's non-TTY invocation returned `Refusing to start the interactive TUI`. Its PTY invocation asked `Continue anyway? [y/N]`. After the screen checkpoints, that p1 revision wrote ESC, `q`, and Ctrl-C, with no Enter. The process exited without an answer, but the key writes were not logged. The current p1 revision sends no keys to `codex agents` and stops it with `killpg`. Whether a session's shell tool can use this interactive command to learn its id is **not measured**. The one PTY run with a session environment stopped at that prompt, and the listing that loaded ran with the probe's environment. That loaded list used titles and cwd without a caller marker, which leaves the ambiguity of option 4. `names_probe_thread` checks for a UUID substring and cannot detect a title-based row. `codex queue --thread` accepts `Session UUID or exact session name`. The `thread/name/set` requirement for `threadId` was read offline from `ThreadSetNameParams` in the schema generated by the 0.159.2 binary with `codex app-server generate-json-schema --out` in `tmp.MmjZz0mpei`. Its properties were `name` and `threadId`. Naming cannot bootstrap identity.

The passing variable was present in the **interactive TUI**, not merely in `codex exec`: every p2 and p4 run launched `codex` in a PTY, and its main notify said `"client": "codex-tui"`. `codex exec` was not probed. p2 run 1, p2 run 2, p2 with `shell_environment_policy.inherit="none"`, and both p4 twins each found `CODEX_THREAD_ID` and `CODEX_SESSION_ID` equal to that session's main notify `thread-id`. In p4, both values differed between the two TUIs sharing one cwd. The `env -i` launch rules out inheritance from the probe process. A dispatched agent can read its own value from its first shell command after start; `tower-dispatch` cannot read it from its launch environment. p2 also logged id-bearing lock and snapshot paths, but this result uses the injected variable and does not rely on Codex rollout files.

The app-server's `thread/list` with a cwd filter enumerated the TUI thread without taking its writer: `codex queue` subsequently reached the same TUI and it replied `AFTER_LIST`. `thread/loaded/list` returned zero. `app-server proxy` exited 1 before the daemon existed and later failed at `initialize` with the daemon running. Enumeration still does not identify the calling session; with two live TUIs, cwd matching returned two records. The title-generation thread did not appear in `thread/list`.

## Recommendation: the main dispatched agent registers its own `CODEX_THREAD_ID`

M5 should instruct the **main dispatched Codex agent** to read `CODEX_THREAD_ID` in its first shell command and pass that value to `tower-register --thread`. This costs one agent tool call and a dispatch-prompt instruction. It also depends on an undocumented internal variable, because only upstream source comments describe its injection. The variable's value is **measured** on codex-cli 0.159.3; reliable compliance with the prompt is **not measured**. The role cannot be woken through `codex queue` until that call runs. The call runs under the measured `CODEX_SANDBOX=seatbelt` and `CODEX_PERMISSION_PROFILE=workspace`. Whether it can write tower's state root (`<git common dir>/tower/...`, outside a linked worktree), and whether a long-lived `tower-register` can continue from a tool call, are **not measured**; these are M5's first checks. A subagent may get its own `CODEX_THREAD_ID` rather than the root's, based on a source comment only; this was **not measured**, so the main agent must register.

`CODEX_THREAD_ID` and `CODEX_SESSION_ID` were equal on every measured main thread. The recommendation uses `CODEX_THREAD_ID` because the SDK README resume example reads it. `exec_env.rs` calls `CODEX_SESSION_ID` the shared root-session identity, so inside a subagent it may hold the root's id, which would remove the subagent risk above. Its subagent value was not measured.

Tower enforces no Codex version floor in code. Its assumed floor is 0.158.0 because [native queue wake](native-channels.md) was measured there. Injection of `CODEX_THREAD_ID` is measured only on 0.159.3. Offline `strings ... | grep -c CODEX_THREAD_ID` counts taken during this spike, against the release binaries under `~/.codex/packages/standalone/releases/`, were 5, 6, 7, and 7 for 0.156.1, 0.158.0, 0.159.2, and 0.159.3 respectively: a binary string is not proof that the variable reaches an interactive tool. This version gap is a risk; this spike does not raise the floor. The variable appears in the Codex SDK README, but not on the public environment-variables page.

## Method incidents
