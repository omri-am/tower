The machine rebooted at 08:36 local time, and no launchd agent starts the daemon again (`launchctl list` in the same pointers section shows only the desktop app and its updater). The [probe](queue-probes/p1_queue_matrix.py) reuses T038's harness from [`lifetime-probes/common.py`](lifetime-probes/common.py) without edits. It starts one throwaway interactive Codex TUI in a fresh fixture under `~/.cache/tower-t038-probes/`, and then sends it one `codex queue` call per case. Most cases differ from `clean_local_bin` in one thing: a flag, the Superset wrapper, or the binary version. `caller_path` differs in two things, the environment and the executable, so a [hand check](queue-probes/logs/hand-checks/2026-10-28-unknown-thread-checks.txt) separates them. [`queue-probes/README.md`](queue-probes/README.md) gives the launcher and the case list.

## The 2026-10-26 failure came through the Superset wrapper

tower's adapter runs `codex queue --thread <id> --message <text>` with the sender's `PATH` (`lib/tower_msg.py`, `ADAPTERS`). The two failed sends to T051 are in [`delivery.log`](queue-probes/logs/field/2026-10-26-implementor-T051-delivery.log) at 14:07:15Z and 14:07:57Z. The Superset wrapper's debug log ([transcription](queue-probes/logs/field/2026-10-26-superset-wrapper-debug.txt)) shows two runs from the same terminal that exited 1 at the same seconds, and one run between them that exited 0. The orchestrator's `codex` on `PATH` was therefore `~/.superset/bin/codex`. Its last line runs the real binary with `--enable hooks` and `--dangerously-bypass-hook-trust` added to every call, `codex queue` included. That line read the same on 2026-10-26 and on 2026-10-28, although Superset rewrote the file at 08:37 local on 2026-10-28. The wrapper is outside this repository, so neither reading is committed.

On 2026-10-26 every `codex` on this machine's `PATH` resolved to 0.164.0: `~/.local/bin/codex` links to `standalone/current`, which pointed at 0.164.0 from 2026-10-25 10:51 local ([transcription](queue-probes/logs/hand-checks/2026-10-26-daemon-running-state.txt)). The card's statement that the failing call ran on 0.162.1 is therefore probably wrong. This is **inferred** from machine state, because the orchestrator's own `PATH` was not recorded.

Run `tmp.TkLL4K3I` reproduced the failure on 0.165.0, with the caller's environment (`caller_path`) and with the wrapper alone (`clean_wrapper`). The [unknown-thread hand checks](queue-probes/logs/hand-checks/2026-10-28-unknown-thread-checks.txt) reproduced it on 0.164.0. Run 5's `caller_missing_thread` shows that the daemon check runs before the thread lookup, so a random thread id gives either the daemon error or `no rollout found`, and queues nothing. On 0.164.0, `--dangerously-bypass-hook-trust` alone (check c) and the wrapper's two flags in the wrapper's position (check d) both gave the daemon error. A `-c` (check b) confirmed the check order on 0.164.0. The daemon was already 0.165.0 during these checks. The check runs in the CLI, so the daemon's version probably does not matter. That is **inferred**.

The version gap between the CLI and the daemon is not the cause. With daemon 0.164.0 running, the 0.165.0, 0.164.0 and 0.162.1 binaries all delivered when they ran without flags.

An idle TUI therefore seems to pick up queued messages on a poll of about 10 seconds. That is **inferred** from the timing, because the poll itself is not logged. The daemon never held the rollout open, so it seems to hand the message to the TUI rather than run the turn itself. That is also **inferred**.

## Question 3: finding the address

A caller needs no lookup. `codex queue --remote unix://` resolves to `$CODEX_HOME/app-server-control/app-server-control.sock`. That path is a symlink to the daemon's listening socket under `/private/tmp/codex-daemon-501/`, and `lsof` shows the daemon listening on the target ([state log](queue-probes/logs/hand-checks/2026-10-28-daemon-running-state.txt)). The daemon runs with `--listen unix://`, its default path. `codex queue --help` lists the accepted `--remote` forms as `ws://host:port`, `wss://host:port`, `unix://` and `unix://PATH` ([help log](queue-probes/logs/hand-checks/2026-10-28-codex-0.164.0-help.txt), from 0.164.0).

To learn whether a daemon runs, a caller can run `codex app-server daemon version`. It exits 0 with `"status":"running"` and `socketPath` while the daemon runs (`daemon_state` in `tmp.TkLL4K3I`). It exits 1 with `Error: failed to connect to ~/.codex/app-server-control/app-server-control.sock` when none runs (`daemon_state` in the other runs). Whether this command writes under `~/.codex/` was not isolated.

## Recommendation for the adapter

The owner decides. The measured options:

1. **Retry with `--remote unix://` only on the daemon error. Recommended.** With no daemon, the plain call delivers, and nothing changes. With a daemon, the plain call from a Superset-hosted sender fails, and `--remote unix://` through the same wrapper delivers (`caller_remote_default`). This costs one extra call only in the failing case, and Codex's own error text names `--remote` as the fix. The retry cannot deliver twice: none of the 9 failed calls in `tmp.TkLL4K3I` left its message in the rollout, whose `rollout_summary` came 131 seconds after the last failed call. It probably also covers other caller-side sources of `-c`: a `-c` with `--remote unix://` passed the daemon check ([hand check](queue-probes/logs/hand-checks/2026-10-28-unknown-thread-checks.txt) h), but delivery with a `-c` was not run. Its risk is that it matches unversioned error text.
2. **Always pass `--remote unix://` when a daemon is found.** This delivers, but every send then needs a detection step, such as `codex app-server daemon version` (one more process per send), because `--remote` fails with exit 1 when no daemon runs.
3. **Remove the override.** Run the first `codex` on `PATH` outside `~/.superset/bin`, as the wrapper's own `find_real_binary` does. That call carries no override. It delivered in both states from a clean environment (`clean_local_bin`). With the caller's environment it passed the daemon check (hand check e, an unknown thread against daemon 0.165.0), but that combination was not run against a live thread. It also stops the wrapper from reporting a Superset `SessionEnd` for every send. But it couples tower to Superset's install layout, and it does not help when another wrapper or alias adds a `-c`.

Today, every send fails while a daemon runs and the sender's `codex` is the Superset wrapper. After `DELIVERY_ATTEMPTS = 3` failures, `return_failed_claim` moves the message to `undeliverable` (`lib/tower_msg.py`). Polling with `tower inbox` still worked during the field test.
