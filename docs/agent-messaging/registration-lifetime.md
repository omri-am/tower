# M5 registration lifetime under Codex

Measured on macOS, 2026-10-14, with the real `~/.codex/packages/standalone/releases/0.162.1-aarch64-apple-darwin/bin/codex` (`codex-cli 0.162.1`) and the model `gpt-6-luna`. That was the installed version when every probe ran: each run's guard required `CODEX_BIN` to resolve to `~/.codex/packages/standalone/current/bin/codex`, logged `"version": "codex-cli 0.162.1"` at start, and logged `installed_after` as `0.162.1-aarch64-apple-darwin` at the end. These are results for **codex-cli 0.162.1**, not a general claim about Codex.

The [probes](lifetime-probes/) reuse T031's harness from [`identity-probes/common.py`](identity-probes/common.py): its PTY launcher, dialog detection, bracketed paste, notify recorder and binary pinning. Each run launched an interactive `codex` TUI under `env -i` with HOME, USER, LOGNAME, SHELL, TERM, LANG, a system PATH, CODEX_HOME and CODEX_BIN, from a fresh `~/.cache/tower-t038-probes/tmp.*` directory. The guard built a throwaway repository `repo/` there, with an excluded `.tower/`, a linked worktree `wt/`, and a `wt/.tower` symlink, as `bin/tower-dispatch:157` makes. Codex started in `wt/`. `bin/tower-locate` resolved `wt` as `ancestor`, and the state root was `repo/.git/tower/root`, outside the worktree. The fixture was not under `$TMPDIR`. T038 assumed that `$TMPDIR` and `/tmp` are default writable roots of Codex's workspace sandbox, which would make question 2 pass for the wrong reason. That assumption is **inference** and was not measured.

In this document, **pass** means that the probe observed the behaviour that the question asks about. **fail** means that the probe observed its absence. **cannot determine** means that the probe did not reach the observation. The probes ran with the owner's real `~/.codex/config.toml`, which sets `default_permissions = "workspace"` (line 1) and defines that profile as `":minimal" = "read"` with write access only to project roots (lines 228-235). This permission profile is the owner's configuration, not a Codex default.

## Survival: only a new session survives the tool call

Each p1 variant ran `tower-register` from one shell command, redirected stdin from `/dev/null` and stdout and stderr to files, and waited up to 5 seconds for the session line before the command returned. Only the detach method changed. `plain` used `&`, `nohup` used `nohup ... &`, `disown` used `nohup ... & disown`, and `setsid` used `/usr/bin/python3 -c 'import os,sys; os.setsid(); os.execv(...)'`, because macOS has no `setsid` binary. The detach method mattered. In both runs, `plain`, `nohup` and `disown` registered, printed a session token, and wrote `agents/<role>.json`, but 3 seconds after the tool call returned their pids no longer existed and the lock was free. The `setsid` holder still held the lock after its own turn, after the following `IDLE_DONE` turn and 30 idle seconds (`after_idle`), and 5 seconds after the TUI was stopped (`after_tui_stop`). Its `ps` row shows PPID 1 and a process group equal to its own pid. `setsid` was the last variant, and the `IDLE_DONE` turn ran no tools. Whether the holder survives later tool calls in the same session was **not measured**. A working M5 agent runs many such calls.

The records of the three failed variants stayed in `agents/<role>.json`. `live_record` treats such a record as not live, because the lock is free. The cause of their death was not observed directly. `bin/tower-register:29-30` handles SIGTERM, SIGINT and SIGHUP by calling `release()`, which deletes the record (`lib/tower_msg.py:148-156`). The records stayed, so those processes did not receive any of these three signals. Their death is therefore **inferred** to come from SIGKILL or another signal that `tower-register` does not handle. The `ps` rows are consistent with Codex ending the command's process group when the tool call returns, because only the variant that left that group survived. This cause is also **inference**. The same handler replaces the SIGHUP ignore that `nohup` sets, so `nohup` cannot protect `tower-register` from SIGHUP in any case. In run [`tmp.Z5YICtxE`](lifetime-probes/logs/tmp.Z5YICtxE/p1_survival.jsonl), whose commands returned immediately after `&` without the wait, no variant wrote a record, `setsid` included. From that one run, a dispatch instruction is **inferred** to need a wait for the session line before the command returns. The cause of that run's result was not observed.

The surviving holder also outlived the agent. `after_tui_stop` shows `"lock_held": true` after the probe sent SIGTERM to the TUI's process group, so the registration stayed live after its session ended. The probe's cleanup then stopped it. Whether a Codex session that exits normally, rather than by SIGTERM, also leaves the holder running was **not measured**.

Question 1 passed only under `--sandbox workspace-write`. That session logged `CODEX_SANDBOX=seatbelt` and no `CODEX_PERMISSION_PROFILE`. From that absence, and from `tower-register` and `python3` starting there, the legacy sandbox mode is **inferred** to have replaced the owner's profile. Under the owner's profile, p1 run [`tmp.qLQFzHy2`](lifetime-probes/logs/tmp.qLQFzHy2/p1_survival.jsonl) could not start any variant. `plain`, `nohup` and `disown` logged `"bash: .../bin/tower-register: Operation not permitted\n"`, and `setsid` logged the `xcode-select: error: No developer tools were found` error from `/usr/bin/python3`. Survival under that profile is **cannot determine**, for the reason that question 2 gives.

## Write access: the state root is outside the sandbox, and so is tower

Under dispatch's default flags the state-root write fails: `mkdir .../repo/.git/tower` returned `Operation not permitted` from inside the linked worktree. Two earlier default-flag runs, [`tmp.fZXckPrF`](lifetime-probes/logs/tmp.fZXckPrF/p2_write_access_default.jsonl) and [`tmp.bnup7Rdc`](lifetime-probes/logs/tmp.bnup7Rdc/p2_write_access_default.jsonl), did not run the command at all. Codex opened the approval selector `1. Yes, proceed (y)` before execution, and the probe stopped without an answer. Those runs passed `-c approvals_reviewer="user"`. A real dispatch passes no such override, so the owner's `approvals_reviewer = "auto_review"` (`~/.codex/config.toml:9`) is **inferred** to send the same request to Codex's automatic reviewer. That routing was not observed. That reviewer may approve the command outside the sandbox. This escalation path was **not measured**, and the Q2 fail covers only the in-sandbox path. Run `tmp.FAa4ZOwk` added "inside the sandbox, without requesting approval or escalated permissions" to the prompt and produced the `mkdir` result in the table.

`--add-dir <common>/tower` makes the state root writable: `mkdir.exit` was `0`. It does not make the registration work. Inside the session, executing `bin/tower-register` from the checkout under `~/.superset/worktrees/` failed with `Operation not permitted`, and `/usr/bin/python3 -c pass` exited 1 with `xcode-select: error: No developer tools were found`. The exec error does not show whether the sandbox denied the read or the exec, so a read denial is **inference**. `tower-register` runs `python3` from `PATH`, not `/usr/bin/python3`. In the `workspace-write` runs, `ps` showed the owner's `~/.pyenv/versions/3.10.4/bin/python3`. Whether that interpreter can start under the owner's profile was not measured. With `--sandbox workspace-write --add-dir <common>/tower`, p1 wrote records and locks under the state root, so the write itself works when the sandbox allows it. The `--add-dir` run [`tmp.xQHCyhX5`](lifetime-probes/logs/tmp.xQHCyhX5/p2_write_access_add_dir.jsonl) ran before the prompt change above, so its prompt lacks the in-sandbox sentence, and the committed `p2_write_access.py` sends a different prompt.

A `codex sandbox -P workspace` diagnostic in the p2 fixture also denied listing `~/.local/bin`, `~/.claude/plugins/cache/tower`, `~/Documents/personal-projects/tower/bin`, `~/.cache` and `$HOME`, and allowed `/usr/bin`. That diagnostic ran in the Claude session, outside a TUI, and its output was not kept as a log. It is supporting evidence only: no verdict rests on it. From it, the installed `tower-register` at `~/Documents/personal-projects/tower/bin/` is **inferred** to be unreadable from a sandboxed session as well, not only this checkout.

## Thread identity and subagents

`CODEX_THREAD_ID` is still injected on codex-cli 0.162.1 and equals the main notify `thread-id`, as T031 found on 0.159.3. The title-generation thread again notified first: `01a139bd-4cba-7393-979d-0212a4b4146a` before the main `01a139bd-3ea4-7251-9119-e56842cf1fab`. `CODEX_SESSION_ID` had the same value as `CODEX_THREAD_ID` on the main thread.

A subagent gets its own `CODEX_THREAD_ID`, and `CODEX_SESSION_ID` holds the root's id in both shells. This matches the `exec_env.rs` comment that T031 cited, which calls `CODEX_SESSION_ID` the shared root-session identity. The subagent's notify carried `"client": null` and its own `thread-id`, `01a139d6-61f5-7251-bbf6-71c76deb0ca2`. Consequence (**inference**): an agent that registers with `CODEX_THREAD_ID` registers whichever thread ran the command, so a subagent registers itself, not the root. `CODEX_SESSION_ID` names the root from either one. T031's recommendation that the main agent registers still holds on this version.

## Recommendation: (a) held lock

Registration should stay an `flock` held by a detached process, because a `setsid`-detached `tower-register` still held its lock at `after_idle` in both p1 runs (`tmp.hB86gB0L`, pid 94178, and `tmp.zwgpP9uQ`, pid 5613, both `"lock_held": true`).

That evidence shows that a held lock can outlive the tool call that started it, so registration needs no lease. Both deciding runs used `--sandbox workspace-write`, which dispatch does not pass. That the same process-group behaviour and the same `setsid` escape apply under the `workspace` profile, once that profile allows tower's reads, is **inference**. M5 is a dispatch-prompt instruction plus a check, but it costs more than "thin":

- The instruction must start a new session (`os.setsid`, because macOS has no `setsid` binary) and wait for the session line before the command returns. `nohup` and `disown` are not enough. The measured `os.setsid` call ran through `/usr/bin/python3`, which failed under the owner's profile, so M5 also needs an interpreter that the sandbox can start.
- Survival was checked only after a turn that ran no tools. Whether the holder survives the agent's later tool calls in the same session was **not measured**.
- The holder outlives the agent. `after_tui_stop` still held the lock, so "the holder is alive" stops meaning "the agent is alive" unless M5 stops the holder at session end. How it does so is M5's decision, and no method was measured here.
- Under the owner's `workspace` profile, no in-sandbox command in these runs could start `tower-register`. The state root needs `--add-dir <common>/tower`. The profile also has to allow tower's files and the `python3` on the session's `PATH`. The other route is escalation through `auto_review`, which was not measured. This precondition applies to every option, because a lease refresh is also a tower command that writes the state root.

A lease would not remove any of these costs. It still needs a tower command inside the sandbox to refresh it. An idle agent that waits for a wake runs no tool calls, so it could not refresh a lease, unless a detached process did it for the agent. That process would be the held lock again. This argument is **inference** and was not measured.

## Method incidents

- No probe answered any dialog or selector, including workspace trust. `lifetime-probes/common.py` wraps T031's `detect_dialog` so that `trust` and `pending_trust` also become `other`, which makes `Run.pump` and `Run.paste` log `dialog_stop` and raise without sending input. Startup update checks were disabled with `-c check_for_update_on_startup=false`, and `-c approvals_reviewer="user"` replaced the owner's `auto_review`, so no automatic reviewer approved anything. Across all 12 logs, the only `pty_write` labels are `bracketed_paste` and `prompt_enter`, each pair before any dialog appeared.
- The first p3 run, [`tmp.0znbt9j4`](lifetime-probes/logs/tmp.0znbt9j4/p3_thread_identity.jsonl), stopped at `Trust this folder?` with the note `Trusting will apply to the repository root`. On 0.162.1, trust is keyed by the repository root, and the owner's `[projects."/Users/omriam"]` entry did not cover the fixture. A real dispatched worktree is **inferred** to resolve to its trusted repository root (`[projects."/Users/omriam/Documents/personal-projects/tower"]`), from that dialog note. No real dispatch was launched to confirm it. Later runs therefore passed a run-only `-c 'projects={"<fixture repo>"={trust_level="trusted"}}'`. This trusted the fixture without a dialog and without a save to `config.toml`.
- p2 run [`tmp.gNgAvncV`](lifetime-probes/logs/tmp.gNgAvncV/p2_write_access_default.jsonl) used an earlier command without the separate `mkdir` and `python3` steps. Its only result is the `tower-register` exec denial. p1 run `tmp.qLQFzHy2` used the owner's profile, had no environment step, and returned without waiting for the session line. p1 run `tmp.Z5YICtxE` used `--sandbox workspace-write` and also returned without the wait. Both are described above and are not the deciding evidence for any verdict.
- The cleanup guard was corrected before the first live run. The Codex worker's first version required `tower-register` in the holder's command line, but `tower-register` execs `python3 - <checkout>/lib <role> ...`. Every run used the corrected guard, which matches the checkout's `lib` path plus the role. Every surviving holder logged `"exited": true, "lock_free": true` in `cleanup`, and `pgrep -fl t038-` found no process after each run.

## What was left in `~/.codex/`

The probes wrote nothing under `~/.codex/` and removed nothing there. Codex itself wrote its usual session state during each live run. The `modified_codex_home_paths` events list the paths only, for example `sessions/2026/...` rollouts, `history.jsonl`, `session_index.jsonl`, `shell_snapshots/`, `thread-writer-locks/`, `state_5.sqlite`, `logs_2.sqlite` and `plugins/cache` (28 paths in `tmp.hB86gB0L`). The managed app-server daemon from T031 is still installed under `~/.codex/packages/app-server-daemon/` (`auto-update-version`, `current`, `install.lock`, `releases`), unchanged. No probe ran `codex agents`. The orphaned pid 634 that T031 reported no longer exists. `~/.codex/config.toml` was read, not changed.
